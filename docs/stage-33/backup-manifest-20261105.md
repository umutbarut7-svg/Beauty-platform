# Signed backup metadata and independent recovery checks

CMS authenticated encryption detects corruption, but anyone with the public
recipient certificate can encrypt a replacement dump. Encryption alone cannot
identify its source or establish that an operator approved this particular backup.
`infra/operations/backup-manifest.py` adds a separate RSA-PSS-SHA256 signature over
canonical JSON metadata and the exact encrypted file's SHA-256 and byte count.
It uses a separate RSA-3072-or-stronger signing key, with a protected passphrase
file supported. No private key is stored in a manifest.

The metadata binds a backup identifier, UTC creation timestamp, application SHA,
snapshot boundary label, recipient certificate DER SHA-256 and signing public-key
SPKI DER SHA-256. Verification requires independent expected values for both key
fingerprints, backup identifier, application SHA, snapshot label and a bounded UTC
creation interval. It rejects future approval windows. These expected values
must come from trusted recovery approval outside the backup store. Copying them
from an untrusted manifest defeats the check. A valid signature proves a claim
by the trusted signer; it does not independently attest the actual database,
snapshot time, source binary, completeness or business authority.

Verification is read-only. It rejects changed signatures, metadata or ciphertext,
unknown fields and algorithms, duplicate JSON fields, oversized metadata, stale
or future claims, unexpected sources and swapped recipient/signer identities.
Regular-file and no-symlink checks remain in force. Signing requires private key
ownership/permissions, checks that the private and public keys match and publishes
a 0600 manifest atomically without overwriting an existing destination. The CLI
prints status only, including on verification failure.

The existing two-boundary PostgreSQL restore workflow now signs the real CMS
dump with a separate temporary fixture key. It rejects eight wrong/missing/
tampered approval contexts before decryption or target database creation, then
verifies the valid manifest before the existing authenticated decryption and
isolated pg_restore. Current-schema quarantine, saved matching cleanup, exact
inventory/B2B snapshots and two real privacy-worker runs remain required.
The independent fixture pins are generated by the harness, not read from the
manifest. They are temporary test identities and establish no production trust.

## Validation and operational boundary

Local validation: 17 signed-manifest tests and the existing 12 CMS tests passed;
the JavaScript harness and Python files passed syntax checks. Actual final-source
CI results must be inspected separately before accepting the database matrix.

The file verifier never decrypts, runs pg_restore, connects to a database/cloud,
creates a scheduler or changes live configuration. The harness uses a private
temporary fixture directory. Production needs immutable local staging between
verification and use, independent signing/recipient custody and revocation,
trusted approval and freshness records, producer exit-status handling, protected
temporary plaintext storage and crash cleanup. A verified manifest does not
authorize reopening a recovered database. Existing withdrawal/account quarantine
and human recovery review remain required.

Off-host durable encrypted backups, retention/RPO/RTO, monitoring, real independent
key recovery and a production restore remain open. This change does not execute
a live backup/restore, migration, rollout, account deletion, real-user operation,
TestFlight upload or provider request. PR47 remains separate and draft. Stage 33
remains **NOT PASS** pending its factual device, quality, privacy and production
operations acceptance.
