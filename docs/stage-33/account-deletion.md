# Account deletion: intake, inspection, erasure and completion receipt

This implementation is a candidate in PR #47, not an enabled production deletion service. Both ACCOUNT_DELETION_PROCESSING_ENABLED and ACCOUNT_DELETION_ERASURE_ENABLED default to false. Apply the additive migrations before rolling out the new API/worker image; authentication reads the quarantine column and maintenance reads the evidence table. No live migration, account mutation, message, provider call, TestFlight update or store submission is performed by this change.

## User path

An authenticated user confirms HESABIMI SIL and verifies the current password to create one owner-scoped request. Request intake preserves access. Wrong passwords return 403; passwords are not stored in the request. After intake, the user can reverify the password to create a 256-bit tracking capability. The database stores its SHA-256 hash; generating a replacement invalidates the previous capability. Rotation is rejected once processing starts.

The login screen can read the receipt after the account has been removed. The capability grants access only to requested/processing/completed status and timestamps. It is not a login credential, never appears in a URL, and reveals no email, owner ID, record body or storage key. There is no automatic email/push delivery claim. The UI instructs the user to keep the code safely.

## Operator path and ownership

The Next.js platform-admin queue lists pending requests, pages results and inspects blockers. Operators must have the current database SUPER_ADMIN role and type ISLEME AL to begin, then KALICI SIL to finalize. The flags remain closed until an operated policy/queue exists. Sole business owners must transfer ownership first. Serializable transactions prevent two owners being frozen together and leaving a business without an available owner. SUPER_ADMIN subjects and restored/quarantined accounts require separate review.

Beginning processing revokes all refresh sessions and prevents old access tokens, login and refresh from authorizing the account. The transaction also takes the photo owner advisory lock, revokes photo permissions, scrubs consultation text/answers/output and records an audit. Delayed photo operations recheck processing under that lock. The existing maintenance worker retries erasure without losing object keys; only a HeadObject 404 after DeleteObject confirms physical removal. Storage denial/outage or a present object remain pending.

## Exact automatic-erasure scope

Automatic finalization is allowed only after processing has started, every account photo is verified erased and its upload safety window has elapsed, and no unreviewed domain record references the account, its customer ID or email. The inspection is derived from every Prisma model and checks exact plain/JSON string identities (with LIKE wildcards escaped, so a different email sharing a prefix does not become a false blocker), including loose String IDs without FKs. Owned rows are excluded only by their actual owner condition, not by skipping whole tables. It returns model names, never record bodies. It is an explicit, rate-limited operator inspection with a bounded transaction; it is not a periodic full-database scan.

Owned User/Customer preferences, sessions, customer reviews, user notification preferences/push devices and private photo/consultation rows can be removed. Other owners' rows are not deleted. Tenantless authentication/authorization/rate-limit facts without metadata keep their type/severity/time but lose actor, request and route links. Security records with tenant context or metadata still block review; they are not overwritten by this exception. Photo analysis/photo/consent rows are removed in FK-safe order only after physical erasure; known per-account photo rate-limit hashes are removed. User deletion cascades owned credentials/profile rows. Unexpired photo consent/event evidence is minimized into AccountDeletionEvidence with its original expiry: policy/notice hash, action, time and hashed source reference. No email, user ID, image or object key is copied. This preserves the previously agreed proof window without retaining the account link or extending the period; the maintenance worker removes expired proof. The request survives through a nullable SetNull owner relation. A completion timestamp and non-identifying operator audit are committed with the deletion. Concurrent retries produce one completion. Any transactional audit failure rolls all database deletion back.

BusinessMember, BusinessCustomer, Appointment, messages, authored business content, finance/audit/governance or any other discovered class blocks automatic completion. There is no unchecked force/retain-forever override. This deliberately does not invent a retention period or erase another party's business history. These cases require an explicit reviewed record-class policy and handling. Simple tenantless auth telemetry is the narrow minimization exception described above; business/security investigations are not silently treated as generic counters. The generic inspection is conservative plain/JSON-reference discovery, not a proof that arbitrary encoded or externally copied data has been erased. Provider processing conditions and production backups are separately governed.

COMPLETED/deletionCompleted=true is returned only after the supported account and its owned database data were actually removed. Blocked cases remain PROCESSING; logging out, revoking permission or physically deleting photos alone never means account erasure. The whole account-deletion release gate remains open while domain-retention cases, the operated processing deadline and actual notification arrangements are unresolved.

## Backup boundary

An older backup can contain a user and request that were deleted/completed after that snapshot. infra/operations/quarantine-restored-accounts.sql requires an explicit offline acknowledgement and exact target database. It marks restored users separately and revokes restored refresh sessions. It neither invents deletion requests nor marks them completed. Old passwords, refresh tokens and access tokens cannot reactivate quarantined users. A valid historical receipt reports RESTORE_REVIEW/deletionCompleted=false until authoritative review; completed snapshots without a user remain completed.

The restore workflow takes real pg_dump snapshots before and after processing, completes the source account erasure, restores into a separate disposable database, applies guarded quarantine twice, and checks the compiled authentication/receipt logic. The worker restart harness also runs against the candidate revision. Both use synthetic local storage with provider flags closed. This does not establish independently durable selective deletion replay, encrypted production backups, a production restore, or permission to reopen a restored live service. Restores must stay offline until authoritative deletion/retention review is resolved.

The earlier photo-cleanup candidate 0227c75 passed 457 API tests, all 20 integration tests, UI review and Android/iOS compilation. New erasure/receipt/quarantine changes have separate local and CI results in PR #47. New checks include real HTTP account deletion and concurrent retry, old-token denial, wrong receipt/password rejection, loose JSON-reference blocking, actual database rollback on completion-audit failure, post-deletion receipt UI, operator queue UI, pg_dump/pg_restore quarantine and real worker crash/restart. Previous manual booking and cancellation acceptance is preserved.
